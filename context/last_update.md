## What Settle is

A hackathon entry for **Briefcase × Stripe, London, 15 Oct 2026, Track 01 "Agents that Spend"**. Finalist demo is tonight at 21:35 (3 minutes on stage; runbook in `docs/LIVE-DEMO.md`).

The pitch: escrow for freelance developers without a human arbiter. The client writes a milestone doc and funds escrow (a Stripe PaymentIntent). The freelancer opens a PR. An agent called **Fluffy** runs the test suite, has two independent LLM verifiers assess each requirement with cited evidence, applies a seven-clause written policy via a deterministic checker, and releases the money as a Stripe Connect transfer the moment every requirement is proven. The core thesis: *the LLM verifies and cites, pure code decides, Stripe moves the money.*

## Architecture

Single Next.js 16 app, ~3,600 lines, no database. The pipeline in `lib/pipeline.ts`:

```
PR → gh fetch + git worktree → vitest (JSON reporter) → recall memory (Cognee + local)
  → verifier A ∥ verifier B (claude-haiku-5-5, forced tool call, different personas)
  → cross-check: every cited test must actually have run and passed
  → checker §1–§7 (pure TS, no I/O)
  → PAY: Stripe transfer (idempotency key = decision id)  |  HOLD: report to PR
  → GitHub comment → write outcome back to memory
```

Separation of powers is deliberate and real in code:

| Module | Role | Holds |
|---|---|---|
| `lib/verify.ts` | Two Haiku verifiers with a strict tool schema; cross-check rejects any test citation that didn't run/pass | No Stripe key |
| `lib/checker.ts` | Pure function. Seven clauses, each returns pass/fail + one-line evidence. `verdict = all pass ? PAY : HOLD` | Nothing |
| `lib/executor.ts` | Only module that moves money. `release()` refuses unless `verdict === "PAY"` or a named human released | Stripe key (restricted key supported via `STRIPE_EXECUTOR_KEY`) |
| `lib/github.ts` | `gh`/`git` via `execFile` (no shell interpolation). Clones into `.settle/`, detached worktree per head SHA | `gh` auth |
| `lib/memory.ts` + `lib/cognee.ts` | Seeds milestone/policy/client history into Cognee; recalls before verifying; writes outcomes after. Degrades to local facts if Cognee is off | Cognee key |
| `lib/store.ts` | JSON-on-disk (`data/runtime.json`), atomic write via tmp+rename | — |
| `lib/wallet.ts` | Freelancer's Connect balance + incoming transfers, read straight from Stripe, 8s cache | — |

Key design choices worth knowing:

- **Decision id is deterministic**: `sha256(milestone | headSha | escrow PaymentIntent | policy version)`. It doubles as the Stripe idempotency key, so replaying a paid decision returns the *same* transfer (§6). Including the escrow ref means a re-funded milestone is a new decision.
- **Transfer is funded by the escrow charge** (`source_transaction`), with decision id, clauses, and verification id in metadata. The Stripe object itself carries the audit trail.
- **Audit row is written before the Stripe call** and updated after (§7).
- **Connect accounts are created with Accounts v2**, with a two-step create → wait for first evaluation → update dance that `docs/INTEGRATION.md` documents as hard-won.

## Things I noticed (not fixed — flagging for you)

1. **Executor key is unrestricted in the live config.** The sidebar reads "test secret key · unrestricted" because `STRIPE_EXECUTOR_KEY` isn't set in `.env`. §7 of the policy and the README's separation-of-powers table both claim a restricted key (transfers:write, balance:read). A judge reading the sidebar chip could catch this. Creating a restricted key in the Stripe dashboard and setting the env var closes the gap in two minutes.

2. **§6 is scoped to a runtime lifetime.** The wallet exposes it: M1 has been paid three times today. Each Reset wipes `payouts` and Seed creates a new escrow, so the "once per milestone" guarantee holds per funding, not per milestone forever. This is defensible ("three demo runs, three escrows") but you should have the sentence ready, because the wallet makes it the most visible thing on screen below the board.

3. **Concurrent verifies can race on `runtime.json`.** `updateRuntime` is read-modify-write on the whole file with no lock. Both Verify buttons are clickable at once; two pipelines interleaving their writes could drop a decision. The demo verifies serially so it's fine, but don't click both.

4. **Test-citation matching is lenient.** `ranAndPassed` in `verify.ts` matches if either string contains the other. A verifier citing `"R4"` matches `"R4 lists invoices paginated"` (intended), but a citation like `"invoice"` would match every test. The prompt instructs exact names so it's low risk tonight; worth tightening after.

5. **`countBaseTests` is a regex count** of `test(`/`it(` on the base branch, compared against vitest's actual count on head. Different measures; fine for this repo (base has 1), could misfire on `test.each`.

6. **ESLint scans `.cursor/skills/` and `.settle/`** — all 41 lint warnings come from there. Add both to `globalIgnores` in `eslint.config.mjs`.

7. **Human release skips §1–§5.** A reviewer can release an unfunded or over-£5k milestone. §7 permits reviewer release, but §5's co-sign rule isn't enforced on that path. Not demo-relevant.

8. The **hydration warning** in the Next.js dev badge is an artifact of my browser tooling injecting `data-cursor-ref` attributes before React hydrated. Not an app bug.
